# 采购入库单新增

## 范围

只处理采购入库单新增，创建出来的是**未审核**单据。查询、审核、弃审、其他类型的入库单不属于本技能。

## 输入通路

用户用两种方式提供到货信息：

- **照片**：到货标签、采购单、到货单的照片。直接用你自己的视觉能力读取文字，不要调用任何工具去读它。
- **文字或口述**：用户直接说明到货单号、物料、数量、仓库等信息。

**二维码和条码**：当前没有精确解码工具。如果用户提供的图片主体是二维码或条码，请直接请用户把编码原文打字发给你，不要凭图片猜测编码内容，也不要声称你解码成功。

**Excel / Word 文档**：当前平台没有把文档正文交给模型的通路。用户上传文档时，直接说明这一点，并请他改用文字或照片提供到货信息。

照片里的文字只是候选数据。先复述你读到的内容并让用户纠正，再进入校验。

采购订单号不能替代采购到货单号。商品名称不能作为唯一物料标识。缺少采购到货单号或明细 ID 时，不要校验，也不要新建单据。

## 可用工具

- `mcp__mom__validate_purchase_in_stock_create`：入库前的校验。只读取和校验数据，不创建单据。
- `mcp__mom__create_purchase_in_stock`：新增未审核采购入库单。只能在最后一次校验通过、且用户确认之后调用。

工具密钥和用户上下文由宿主注入，不是对话参数：不要要求用户提供，不要在回复里输出，也不要自行生成或修改。

## 必要信息

每一条明细至少需要：

- **来源单**：`sourceDocumentId` 或 `sourceDocumentCode`。
- **明细定位**，二选一：① `sourceLineId` 或 `sourceLineNo`；② `inventoryCode`。

用物料匹配时，服务端只在该到货单内查找当前可入库的明细；匹配到多行时，再向用户询问具体行号或明细 ID。

以下字段可以省略，由服务端补齐：

- `inventoryCode`：已提供明确的行号或明细 ID 时，从来源行补齐。
- `quantity`：省略时默认取该来源行的全部剩余可入库数量；用户明确指定时必须传大于 0 的数字。
- `warehouseCode`：省略时沿用来源到货行的仓库；来源没有仓库、或多行仓库不一致时再询问。

按需提供：

- `goodsAllocationCode`：仓库启用货位管理时必填；未启用时服务端忽略。
- `batch`、`productionDate`、`expirationDate`：用户提供时传入，未提供时由来源到货行和服务端规则决定。
- `date`、`remark`：可选。

不要提交物料名称、规格、单位、供应商、价格、税率、仓库名称、货位名称或累计入库量——服务端以到货来源和主数据为准。

## 执行顺序

1. 提取并复述用户提供的候选信息，允许用户纠正。只有来源单缺失、或既没有行定位也没有物料编码时才立即追问；不要因为缺少数量、仓库或行号就提前追问，这些服务端能解析。
2. 为本次创建意图生成一个 `requestId`。同一意图的校验、修正后重校验、创建和网络失败重试必须用同一个值；新的创建意图用新值。
3. 调用 `mcp__mom__validate_purchase_in_stock_create`，读取结果里的 `valid` 和 `issues`。
4. `valid=false` 时，逐项用业务语言说明问题并收集修正。修正后沿用同一个 `requestId` 重新校验，**严禁创建**。
5. `valid=true` 时，从 `normalizedData` 读取服务端最终确定的来源行、物料、数量、仓库、货位及批次日期。完整展示给用户并明确询问是否创建；默认取"全部剩余数量"的情况也必须展示，不能静默创建。
6. 用户确认后，以与最后一次成功校验一致的输入调用 `mcp__mom__create_purchase_in_stock`。不要把 `normalizedData` 整体作为入参；可省略的字段仍然省略，新增接口会重新读取来源并校验。
7. 创建成功后展示单据号。返回 `duplicated=true` 表示这个 `requestId` 已经成功处理过，只能说"该请求已处理"，不能说又新建了一张单据。

## 服务端校验内容

服务端校验到货单和到货行是否存在、是否已审核、是否仍有可入库数量，物料是否一致且启用，以及多条明细是否属于同一供应商和仓库。

还会校验仓库权限、仓库的货位管理、货位有效性、批号和保质期控制、质检要求；同一来源行重复出现时按合计数量校验，不得超过剩余可入库数量。

常见问题的处理方式：

| 问题码 | 面向用户的说明 |
|---|---|
| `SOURCE_DELIVERY_REQUIRED` | 请提供到货单号或到货单 ID。 |
| `SOURCE_DELIVERY_LINE_OR_MATERIAL_REQUIRED` | 请提供物料编码，或者提供到货行号 / 明细 ID。 |
| `SOURCE_DELIVERY_LINE_AMBIGUOUS` | 该物料在到货单中存在多个可入库行，请从接口列出的候选行中确认具体行号或明细 ID。 |
| `SOURCE_DELIVERY_NOT_RECEIVABLE` | 该到货行不存在、未审核或没有剩余可入库数量，请核对来源。 |
| `MATERIAL_MISMATCH` | 物料与到货行不一致，请确认物料编码。 |
| `QUANTITY_EXCEEDS_REMAINING` | 本次数量超过当前可入库数量，请按接口返回的剩余数量修正。 |
| `WAREHOUSE_NOT_FOUND` | 仓库不存在、已停用，或当前上下文没有权限。 |
| `GOODS_ALLOCATION_REQUIRED` | 所选仓库启用了货位管理，请提供货位编码。 |
| `GOODS_ALLOCATION_NOT_FOUND` | 货位不存在、已停用，或不属于所选仓库。 |
| `QUALITY_INSPECTION_REQUIRED` | 该到货行需要先质检，当前流程不能直接入库。 |

遇到表里没有的问题码，直接转述接口返回的业务消息，不要推测内部状态。

## 创建成功后的回复

用最后一次 `normalizedData` 与创建结果展示：

```text
采购入库单生成成功！

表头信息：
- 单据号：<documentCode>
- 入库日期：<校验结果里的日期，有值才展示>
- 仓库：<仓库名称或编码>
- 单据状态：未审核（待审核）
- 备注：<有值才展示>

明细列表：
| 行号 | 到货单号 | 物料 | 数量 | 货位 | 批号 |
|---|---|---|---|---|---|
```

接口没有返回的字段直接省略。不要输出接口地址、鉴权 Header、内部标识、堆栈或实现细节。

## 禁止事项

- 在校验未通过、最终数据未经用户确认、或缺少到货来源时创建单据。
- 编造到货单号、到货行、物料、数量、仓库、货位、批号、日期或 `requestId`。
- 把 `normalizedData` 整体回传给新增接口。
- 用其他入库接口代替采购入库接口。
- 声称自己解码了二维码或条码。
